# Notion 追記案（FREE WAN 大阪北区店）

Notion へそのまま貼れる形にしてあります。**秘匿情報（ドメイン・IP・SSH ユーザー・各種トークン・
パスワード）はここに書いていません。** Notion 側でも、その手の値は Bitwarden などに置き、
Notion にはリンクだけを残す運用を推奨します。

## 1. システム環境

### 構成

| 項目 | 内容 |
|---|---|
| 稼働形態 | GCP の VM 1台。Docker Compose（`standalone` プロファイル）で app・db・caddy を起動 |
| アプリ | Node.js（LTS）/ Express。ESM。フレームワークなし |
| データベース | PostgreSQL。マイグレーションは素の SQL（`src/db/migrations/NNN_*.sql`）で、**コンテナ起動時に自動適用** |
| HTTPS | Caddy が自動取得・更新。ドメインは DuckDNS |
| 顧客への配信 | LINE 公式アカウント（Messaging API）。予約フォームは LIFF |
| スタッフ通知 | LINE グループ（`STAFF_NOTIFY_CHANNEL=line`）。Slack にも切替可 |
| AI 利用 | Claude Haiku。スタッフのシフト変更申請の読み取りと、来店フォロー返信の分類のみ |
| 管理画面 | `/mock/`（Basic 認証の内側）。単一 HTML。外部ライブラリ・フォント・画像を読み込まない |
| タイムゾーン | アプリ・cron とも `TZ=Asia/Tokyo`。DB は TIMESTAMPTZ |

### リポジトリとデプロイ

- リポジトリ: `emcyrup/freewan`（**公開設定**。ホスト名・IP・認証情報は書かない）
- `main` に push すると GitHub Actions が **テスト → 全店舗の VM へ SSH デプロイ** まで自動実行
- 配布先は Secret `DEPLOY_TARGETS`（`user@host` の改行区切り）。1台が失敗しても他店舗は止まらない
- デプロイ後は `/health` で起動確認まで行う

### 環境変数（`.env`。値はサーバー上のみ）

| 分類 | 変数 |
|---|---|
| 必須 | `POSTGRES_PASSWORD` `DOMAIN` `DATABASE_URL` `LINE_CHANNEL_ACCESS_TOKEN` `LINE_CHANNEL_SECRET` `LIFF_ID` `LIFF_CHANNEL_ID` `ADMIN_USER` `ADMIN_PASSWORD` |
| 送信制御 | `SEND_MODE`（`dry_run` / `test` / `live`）、`TEST_LINE_USER_ID` |
| 通知 | `STAFF_NOTIFY_CHANNEL` `STAFF_LINE_GROUP_ID` `SLACK_WEBHOOK_URL` |
| AI | `ANTHROPIC_API_KEY` |
| 配信条件 | `PRE_REMINDER_DAYS_BEFORE=2` `AFTER_VISIT_DAYS_AFTER=7` `DORMANT_DAYS=90` `DORMANT_DAILY_LIMIT=50` `TICKET_NUDGE_IDLE_DAYS=14` `PLAN_NUDGE_IDLE_DAYS=7` `VACCINE_REMIND_DAYS=30` `VACCINE_ACTIVE_DAYS=180` |
| 写真配信 | `PUBLIC_BASE_URL`（未設定なら `DOMAIN` から導出。無いと来店お礼を送らない） |
| SNS | `IG_USER_ID` `IG_ACCESS_TOKEN` `IG_POST_MODE` / `THREADS_USER_ID` `THREADS_ACCESS_TOKEN` `THREADS_POST_MODE` |
| 店舗情報 | `STORE_NAME` `STORE_TAGLINE` `STORE_LOGO` `STORE_OPEN_TIME` `STORE_CLOSE_TIME` `STORE_CLOSED_DAYS` `STORE_ADDRESS` `STORE_PHONE` |

> **店舗ごとにコードを分岐させない方針。** 差分は `.env` と `scripts/store-data/*.json`（メニュー・コース）に寄せてある。
> 5店舗展開時もこの2つを差し替えるだけで増やせる。

### 誤爆防止の仕組み（重要）

- 送信は `SEND_MODE` の3段階で制御。**現在は `live`（本番送信）**
  - `dry_run` … 送らずログに出すだけ（既定値）
  - `test` … 宛先を `TEST_LINE_USER_ID` に固定（`TEST_LINE_USER_ID` 未設定だと起動しない）
  - `live` … 本番送信
- 送信は必ず `message_logs` に先に記録してから実施。`dedupe_key` の UNIQUE 制約が二重送信を止める
- ログに顧客の氏名・電話番号・LINE userId を出さない（内部 id で参照）
- 配信は毎朝 10:00（来店お礼のみ 19:00）。深夜・早朝の送信は行わない

## 4. 運用開始までに店舗側で必要なこと

1. **既存顧客台帳（氏名・電話番号）の投入** … LINE 登録時の自動ひも付けに直結するため最優先
2. スタッフの登録と LINE 連携（シフト申請に必要）
3. スタッフ用 LINE グループへの Bot 招待（スタッフ通知の届き先）
4. リッチメニューの登録（画像 2500×843px）
5. `ANTHROPIC_API_KEY` の設定（無いとシフト申請が読み取れない）
6. LINE の通数プラン確認（無料枠は月200通。配信対象が増えると超える）
7. 本番の公式アカウントへの切り替え（現在はテスト用チャネル）

## 5. 店舗へ確認したい運用ルール

- 回数の消化順は「当月分優先」でよいか（繰越分が失効しやすくなる）
- 繰越は1ヶ月でよいか
- 月途中の加入は満額か日割りか（現在は満額）
- 解約後の残回数は期限まで使えるままでよいか
- 「時間休」の入力粒度（30分単位か1時間単位か）
- トリマー実績の「貢献売上」の定義（指名のみか、担当施術の合計か。物販を含むか）
- 体験後の追客を何日おきに何回まで行うか
